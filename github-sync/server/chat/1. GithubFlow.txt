GitHub to S3 Real-Time Data Pipeline - Implementation Plan

Overview

Build a production-ready, event-driven pipeline to fetch GitHub data (Organizations, Users, Repositories, Commits,
Pull Requests) via GitHub REST API, stream through Kafka, and store in AWS S3 with date-partitioned structure
optimized for Spark processing and TimescaleDB ingestion.

Architecture Summary

GitHub API → Fetcher Service → Kafka Topics → Consumer Service → S3 (Parquet + JSON)
                                                                        ↓
                                                                Spark Processing
                                                                        ↓
                                                                TimescaleDB

File Format Strategy

Dual-format approach for flexibility:

1. Parquet (processed/) - Primary format for analytics
- Columnar storage optimized for Spark
- 50-80% compression vs JSON
- Schema enforcement
- Efficient filtering/aggregations
2. JSON Lines (raw/) - Raw data lake
- Human-readable for debugging
- Event replay capability
- Line-delimited for streaming

Kafka Topics Architecture

Raw data topics (GitHub API responses):
- github.organizations.raw
- github.users.raw
- github.repositories.raw
- github.commits.raw
- github.pull_requests.raw

Processed data topics (normalized/enriched):
- github.organizations.processed
- github.users.processed
- github.repositories.processed
- github.commits.processed
- github.pull_requests.processed

Control topics:
- github.fetch.commands - Trigger fetch operations
- github.errors.dlq - Dead Letter Queue for failed messages

Partitions: 3-12 per topic based on volume (commits=12, repos/PRs=6, orgs/users=3)

Critical Files to Implement

1. Github/shared/config.py

Purpose: Central configuration management using Pydantic Settings
- Load from .env file (GitHub PAT, AWS credentials)
- Type-safe settings with validation
- Environment-specific configs (dev/staging/prod)
- Default values for all settings

2. Github/clients/github_client.py

Purpose: GitHub REST API client
- Authentication with PAT token
- Rate limit handling (5000 requests/hour)
- Exponential backoff retry logic
- Link header pagination
- Error handling (401, 403, 404, 429, 5xx)

3. Github/models/base.py

Purpose: Base Pydantic model for all entities
- Common fields: fetched_at, entity_type, pipeline_version
- JSON serialization/deserialization
- Schema generation for documentation
- Validation rules

4. Github/producers/github_producer.py

Purpose: Kafka producer for GitHub data
- Serialize to JSON
- Partition by entity key (owner/repo/sha)
- Retry logic with tenacity
- Metrics tracking (messages sent, failures)
- DLQ for permanent failures

5. Github/consumers/s3_writer.py

Purpose: Kafka consumer → S3 uploader
- Consume from multiple topics
- Micro-batching (accumulate 100 msgs or 60s)
- Transform JSON → Parquet with PyArrow
- Upload to S3 with date partitioning
- Manual offset commit after successful S3 upload

Error Handling Strategy

Transient Errors (Retry with exponential backoff):
- Network timeouts
- GitHub rate limits (429)
- Temporary 5xx errors
- Kafka broker unavailable

Permanent Errors (Send to DLQ):
- 401/403 Authentication failures
- 404 Resource not found
- Invalid data schema
- S3 permission errors

Retry Configuration:
- Max retries: 3
- Base delay: 1s
- Backoff factor: 2
- Max delay: 60s

Key Implementation Details

Rate Limiting

- GitHub limit: 5000 requests/hour (authenticated)
- Strategy: Monitor X-RateLimit-Remaining header
- Sleep when < 100 requests remaining
- Handle 429 with retry after X-RateLimit-Reset

Pagination

- Use Link header pagination (rel="next")
- Max 100 results per page
- Fetch all pages for complete datasets

Kafka Configuration

Producer:
- acks='all' - Wait for all replicas
- compression_type='snappy' - Fast compression
- batch_size=32768 - 32KB batches
- linger_ms=100 - 100ms batch window

Consumer:
- enable_auto_commit=False - Manual commit
- max_poll_records=500 - Batch processing
- auto_offset_reset='earliest' - Start from beginning

Micro-Batching

- Accumulate 100 messages OR 60 seconds (whichever first)
- Single S3 upload per batch
- Reduces S3 PUT costs
- Improves throughput
