Kafka-Based GitHub Data Synchronization System - Implementation Plan

Overview

Build a production-ready continuous GitHub data fetching system that:
- Uses Kafka to buffer API requests and prevent rate limit violations (5000 req/hour)
- Operates separate Kafka topics per resource type (orgs, repos, commits, pulls)
- Stores data in S3 with repository-based folder structure
- Batches uploads (10-50 records or 30-60 seconds) for efficiency

System Architecture

Scheduler Service (APScheduler)
    ↓ (fetches data periodically)
Rate Limit Manager (Redis-backed)
    ↓ (checks before each API call)
Enhanced GitHub Client
    ↓ (publishes to Kafka)
Kafka Topics (github-orgs, github-repos, github-commits, github-pulls)
    ↓ (consumed by workers)
Consumer Workers (4 workers, one per topic)
    ↓ (batch accumulation: 50 records OR 60 seconds)
S3 Client
    ↓ (uploads to S3)
S3 Bucket: s3://github-scm/{owner}/{repo}/{data_type}/{timestamp}.json.gz

Phase 2: Rate Limit Management

Goal: Prevent GitHub rate limit violations with intelligent throttling

File: sync/core/rate_limiter.py

Key Features:
- Parse GitHub response headers: X-RateLimit-Remaining, X-RateLimit-Reset
- Use Redis to store rate limit state (enables multi-process coordination)
- Block requests when remaining < 100 (safety buffer)
- Calculate sleep time until reset window
- Exponential backoff on 429 responses: 1s, 2s, 4s, 8s, 16s, 32s

Methods:
class RateLimitManager:
    def __init__(self, redis_client: Redis, buffer: int = 100)
    async def update_from_headers(headers: dict) -> None
    async def can_make_request() -> bool
    async def wait_if_needed() -> None  # Blocks if needed
    def get_wait_time() -> float

Redis Keys:
- github:ratelimit:remaining - Current remaining requests
- github:ratelimit:reset - Unix timestamp of reset time
- github:ratelimit:limit - Total limit (5000)

Phase 4: Kafka Producer

Goal: Reliable message publishing with proper partitioning and error handling

File: sync/kafka/producer_manager.py

Key Features:
- Singleton KafkaProducer instance (connection pooling)
- Topic-specific publish methods: publish_org(), publish_repo(), publish_commit(), publish_pull()
- Partition key strategy: org.login for orgs, repo.full_name for repos/commits/PRs
- Compression: gzip
- Exactly-once semantics: acks='all', enable_idempotence=True
- Retry configuration: 3 retries, max 5 in-flight requests

Message Schema:

}

File: sync/kafka/dlq_handler.py

Purpose: Route failed messages to Dead Letter Queue after 3 retries

Phase 7: Kafka Consumers

Goal: Consume messages, batch accumulate, and upload to S3

File: sync/consumers/base_consumer.py

Base Consumer Logic:
class BaseS3Consumer:
    def __init__(self, topic, s3_client, batch_size=50, batch_timeout=60)

    async def consume() -> None:
        # Main loop
        while True:
            messages = self.consumer.poll(timeout_ms=1000)

            # Add to buffer
            for record in messages:
                self.buffer.append(record.value)

            # Check batch conditions
            if len(buffer) >= 50 OR time_since_last_upload >= 60:
                await upload_batch()
                consumer.commit()  # Manual offset commit

Monitoring & Observability

Metrics to Track:
- Requests made per hour (should stay < 5000)
- Rate limit remaining (warn if < 200)
- Messages published per topic
- Consumer lag per topic
- Batches uploaded to S3
- DLQ message count (alert if > 0)

Logging Strategy:
- Use structlog for structured JSON logs
- Log levels: INFO for normal ops, WARNING for rate limit approaching, ERROR for failures
- Include context: sync_id, topic, owner/repo, rate_limit_remaining

Edge Cases Handled

1. Rate Limit Exhaustion: Block all requests until reset window
2. Large Repositories: Pagination handled by fetcher classes
3. Network Failures: S3 upload retry with exponential backoff (max 5 attempts)
4. Kafka Broker Down: Producer retry with different broker
5. Consumer Crashes: Offset not committed, messages replayed on restart
6. Duplicate Messages: Idempotent S3 uploads (timestamp in filename)
7. GitHub API 429 Responses: Exponential backoff, update rate limiter
8. Empty Batches: Only upload if buffer length > 0

Security Considerations

- ✅ AWS credentials in .env (should use IAM roles in production)
- ✅ GitHub token rotation (manual process, document in README)
- ✅ Redis password protection (add in production)
- ✅ S3 bucket encryption at rest (enable via AWS console)
- ✅ Kafka message encryption (optional, for sensitive data)

Production Deployment Notes

- Deploy scheduler as single instance (use Redis leader election if multi-instance)
- Deploy multiple consumer instances per topic (scale horizontally)
- Use Kafka replication factor = 3 in production
- Enable S3 versioning for data recovery
- Set up CloudWatch alarms for DLQ messages, rate limit warnings
- Use AWS Secrets Manager instead of .env for credentials
- Enable Kafka message retention = 7 days (balance storage vs replay capability)
