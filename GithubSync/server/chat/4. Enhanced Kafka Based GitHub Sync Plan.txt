Enhanced Kafka-Based GitHub Data Synchronization System - Implementation Plan

Overview

Build a production-ready continuous GitHub data fetching system that:
- Uses Kafka to buffer API requests and prevent rate limit violations (5000 req/hour)
- Operates separate Kafka topics per resource type (orgs, repos, commits, pulls)
- Stores data in S3 with repository-based folder structure
- Batches uploads (50 records or 60 seconds) for efficiency
- Includes webhook support for real-time updates (90% API call reduction)
- Handles all critical edge cases (secondary limits, rebalancing, failures)

Key Enhancements:
✅ Webhook support for real-time updates
✅ Conditional requests with ETag caching
✅ Secondary rate limit handling (concurrent requests, CPU time)
✅ Consumer rebalancing protection
✅ Distributed locking for scheduler
✅ Strong idempotency (content hash + timestamp)
✅ Incremental sync support

Phase 2: Enhanced Rate Limit Management

Goal: Prevent GitHub rate limit violations with intelligent throttling + secondary limits

File: sync/core/rate_limiter.py

Key Features:
- Parse GitHub response headers: X-RateLimit-Remaining, X-RateLimit-Reset
- Use Redis to store rate limit state (enables multi-process coordination)
- Block requests when remaining < 100 (safety buffer)
- Calculate sleep time until reset window
- Exponential backoff on 429 responses: 1s, 2s, 4s, 8s, 16s, 32s
- Track concurrent requests (max 5) - SECONDARY RATE LIMIT
- Circuit breaker for abuse detection
- Use Redis server time to avoid clock skew

Methods:
class RateLimitManager:
    def __init__(self, redis_client: Redis, buffer: int = 100)
    async def update_from_headers(headers: dict) -> None
    async def can_make_request() -> bool
    async def wait_if_needed() -> None  # Blocks if needed
    async def acquire_request_slot() -> bool  # For concurrent limit (max 5)
    async def release_request_slot() -> None
    async def check_secondary_limits() -> bool  # Concurrent + CPU time
    def get_wait_time() -> float
    def get_server_time() -> float  # Use Redis time, not local

Redis Keys:
- github:ratelimit:remaining - Current remaining requests
- github:ratelimit:reset - Unix timestamp of reset time
- github:ratelimit:limit - Total limit (5000)
- github:ratelimit:concurrent - Current concurrent requests (max 5)
- github:ratelimit:circuit_open - Circuit breaker state

Phase 6: Scheduler Service with Distributed Locking

Main Methods:
class GitHubSyncScheduler:
    def __init__(
        self, 
        producer: GitHubKafkaProducer, 
        rate_limiter: RateLimitManager,
        redis: Redis
    )
    async def start() -> None  # Start all scheduled jobs
    async def stop() -> None
    async def acquire_scheduler_lock() -> bool  # NEW - distributed lock
    async def fetch_and_publish_orgs() -> None
    async def fetch_and_publish_repos() -> None
    async def fetch_and_publish_commits() -> None  # Incremental sync
    async def fetch_and_publish_pulls() -> None  # Incremental sync

Logic Flow:
1. Acquire distributed lock (Redis SET NX with TTL)
2. Read org/repo list from sync_targets.yaml
3. For each target:
   a. Check rate limit → acquire request slot
   b. Get last_sync timestamp from Redis (incremental sync)
   c. Call appropriate fetcher with "since" parameter
   d. Fetcher checks rate limit → makes API call → updates rate limit
   e. Publish result to Kafka topic
   f. Update last_sync timestamp in Redis
   g. Release request slot
4. Log metrics (request count, rate limit status)
5. Release distributed lock

Edge Cases Handled (Enhanced)

1. Rate Limit Exhaustion: Block all requests until reset window
2. Secondary Rate Limits: Track concurrent requests (max 5), circuit breaker
3. Large Repositories: Pagination handled by fetcher classes, streaming for huge repos
4. Network Failures: S3 upload retry with exponential backoff (max 5 attempts)
5. Kafka Broker Down: Producer retry with different broker
6. Consumer Crashes: Offset not committed, messages replayed on restart
7. Consumer Rebalancing: Don't commit during rebalance, detect rebalancing state
8. Duplicate Messages: Strong idempotency (content hash + timestamp), check Redis before processing
9. GitHub API 429 Responses: Exponential backoff, update rate limiter
10. Empty Batches: Only upload if buffer length > 0
11. Multiple Scheduler Instances: Distributed lock prevents duplicates
12. Clock Skew: Use Redis server time for rate limit calculations
13. S3 Upload Failures: Transactional batch processing, store state in Redis
14. Webhook Delivery Failures: Idempotency keys, retry logic
15. Pagination Interruption: Store pagination state in Redis, resume on restart

- Deploy multiple consumer instances per topic (scale horizontally)
- Deploy webhook receiver behind load balancer (multiple instances)

- Use AWS Secrets Manager instead of .env for credentials
- Enable Kafka message retention = 7 days (balance storage vs replay capability)
- Monitor webhook delivery success rate and retry failed deliveries
- Set up alerting for distributed lock conflicts (indicates multiple scheduler instances)
